B · Errors that teach — without lying about the compiler

The evidence is deliberately modest: enhanced messages improve confidence and reduce repeated errors, but do not reliably improve fix-rate. So the design promise is one plain sentence, one action, raw output preserved underneath — and "Explain with AI" visible from the first diagnostic instead of appearing only after a failure.

NewB1 · P0-5 · The beginner line above the log

Four lines maximum: what went wrong in words, where, the one next action, and a door to the explanation. The compiler's own words stay, dimmed and intact, below.

Why: Becker et al. (2016) — structure and placement beat length; NN/g heuristic 9 — plain language, precise problem, constructive solution, placed next to the cause. Existing pieces to reuse: the diagnostics parser, the jump target, and the single remedy chip that today exists only for the semicolon.

NewB2 · The pure table behind B1

A host-testable table, ~20 first-week C errors (plus Python/JS where the app can see them). Every row: one sentence, one action, one chapter. No AI needed; the AI door is an option, not the mechanism.

BeginnerDiagnostics (pure, host-tested)
expected ';' → “A statement is missing its ending.” expected declaration → “Something is spelled wrong, or a { } is unbalanced.” implicit declaration → “This function needs its #include at the top.” format '%d' expects int → “%d prints whole numbers; use %f for decimals.” uninitialized variable → “This value is read before anything is put in it.” segmentation fault → “The program used memory it does not own (often a bad index).” …
Every explanation goes through one wording check: present tense, active voice, ≤25 words, no word a beginner has not met yet — or the jargon itself bracketed in plain words (COGA).

Honesty clause for the phase doc: this improves comprehension and confidence, not necessarily fix-rate. Write it that way.

Jargon arrives before grammar in the first minutes ("userland", "packages", "repository", "toolchain"). The fix is a reusable inline explanation — never floating over content — plus a single vocabulary (Appendix C of the dossier) applied everywhere.

NewD4 · Colour-blind-safe diff, behind the same switch

~8% of men have some red–green colour-vision deficiency, and Git diffs are the most red/green-coded surface an IDE has. One optional theme variant — added/removed keep a redundant + / − and a word, never hue alone.

Default
+ faster = 2
− faster = 5
Colour-safe (teal / vermillion)
+ faster = 2 added
− faster = 5 removed

Why: Modus (Emacs) ships deuteranopia and tritanopia variants for exactly this reason; the + / − gutter keeps meaning when hue collapses.

E · The practice loop, drawn small on purpose

Worked examples, Parsons problems and PRIMM all say the same thing: novices learn fastest by reading, predicting, running, and changing code that already works. CodeC already ships the perfect subject (the Arcade sample). This is a content card, not an XP system.

ProposalE1 · P2-1 · Predict → run → change

Attachment before the first run, not a separate mode. Two questions and one edit; state lives in a JSON next to the project; no scores, no streaks, no pressure.
