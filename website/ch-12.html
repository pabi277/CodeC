Networking & SSH

Fetch deliberately, understand loopback and share a local preview without promising an unshipped SSH client.

What you will learn

  • Use verified curl/wget tools and read a network result.
  • Distinguish local-only preview, LAN sharing and public hosting.

Before you begin

Ready Linux userland; internet for public fetches; a non-sensitive HTML project for LAN practice.

Start with the actual tools

This chapter follows the verified networking variant: curl is in the bootstrap seed, wget is a curated package root, and Git uses HTTPS. OpenSSH is explicitly deferred in the current package config. There are no ssh-keygen or SSH-login instructions pretending it is installed. SSH is an encrypted remote-shell protocol; it needs a client and a server, not just an IDE.

Check local availability

command -v curl
command -v wget

Expected: paths for installed tools; missing wget means install it if desired with pkg install wget. Never add official Termux repositories to fill a gap.

Read headers, then save a page

Read a known public response

curl -I https://github.com/pabi277/CodeC/releases

Expect an HTTP status and headers such as content-type; their precise values and protocol version vary. A redirect is not the same as a failure. Do not disable TLS verification as a routine fix.

Save into a new practice file

curl -L --fail -o releases.html https://github.com/pabi277/CodeC/releases
ls releases.html

Expected: a saved HTML file if the request succeeds. --fail reports HTTP errors; -L follows redirects. This deliberately contacts GitHub. Inspect downloads before executing anything—this file is a page, not a script to run.

An optional second downloader

Install and use wget

pkg install wget
wget -O repo-page.html https://github.com/pabi277/CodeC

Expected: a saved repository page or a named network error. Both downloaders depend on connectivity, DNS, certificates and server policy. A captive portal or locked network can fail independently of CodeC.

127.0.0.1 means this device

CodeC serves a static project over a local HTTP server for Web Preview. A loopback URL on your phone points to your phone; the same URL typed on a second device points to that second device. Relative CSS, JavaScript, modules and fetch work against the project’s local origin.

Do not hard-code a port from a screenshot. RUN opens the current project’s preview and shows its actual endpoint.

A careful LAN-sharing exercise

  1. Open a harmless HTML project and RUN index.html. Keep the local page working before adding another device.
  2. Enable LAN sharing in the preview/server controls. The panel has On this phone and Other devices; use the latter URL or QR on a device on the same Wi-Fi.
  3. Keep the CodeC server running. If unreachable, check Wi-Fi client isolation and the displayed LAN address, not the loopback URL.
  4. Turn sharing off when finished. Reachable peers can request served project files; never use a sensitive project for this test.

A foreground service helps keep serving, but Android battery policies still matter. LAN mode is not public internet hosting or an authentication boundary.

Try it yourself

  1. Save the public release page and name two response headers. Expected: a file and a status you can explain, or a recorded network failure.
  2. Identify the two preview addresses and explain why only one is for another device.
  3. If a second device is available, open the harmless page via LAN and then disable sharing. Expected: local preview remains your primary workflow; no public deployment claim.

Common mistakes

  • Do not assume OpenSSH ships just because the chapter discusses SSH.
  • Never paste a phone loopback URL into another device and expect the phone’s server.
  • Downloading text is not permission to execute it; inspect code and keep TLS checks intact.
