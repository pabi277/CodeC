What you will learn

  • Separate read tools, edit approval and run approval.
  • Use caps, controls and Undo without mistaking them for unrestricted powers.

Before you begin

There is no write tool and no exec tool. request_run asks; it does not run. Search scope can only narrow the admitted walk, not discover secret paths outside it. Expand a timeline row for exact result text, bounded before it becomes context in a later request.

Refusals are features

Secret-like names (.env, .npmrc, private keys), .git, .codec, build outputs and symlink escapes are refused before reading. Discuss these names without creating or uploading a real secret. A path or cap refusal is a boundary to respect, not a puzzle to bypass.

The agent has no independent Android permission. It uses an admitted project scope and explicit user approval routes; provider/model capability flags do not broaden those rights.

Door one: Apply or Reject

Ask for a small wording change to a greeting in your disposable hello.c. Read the per-file diff and selected files. First choose Reject changes and inspect the file: expected result is no change. If you request it again and choose Apply, only the reviewed proposal should be written through CodeC’s dedicated applier.

After applying, Undo AI changes can restore the last task’s bounded preimages (at most 5 files/256KB). Intervening manual edits can cause a conflict; do not overwrite them to make a test look green. Undo does not roll back commands, network requests, package changes or Git operations.

Door two: Run or Skip

Ask for a run of the harmless program. Inspect the approval card, then choose Skip. Expected: no execution. If you later choose Run on known safe code, it enters CodeC’s normal RUN pipeline; bounded real output and exit status can return to the configured provider.

This is not terminal typing, a package installer or automatic Git staging/committing. Send, Apply and Run are distinct decisions. An AI answer saying “passed” is not evidence that a run occurred.

Nine controls, one safety boundary

  • Read window: smaller file slices, within 50–400 lines.
  • Working set: context depth within admitted paths.
  • Task memory: bounded task facts, not raw-chat persistence.
  • Answer detail: presentation, not more permissions.
  • Tool activity: display of the timeline.
  • Request inspection: always on; cannot be disabled.
  • Backup provider: a manual offer, never a silent transfer.
  • Budget extension: an offer inside the hard caps.
  • Read-only reviewer: review without new write/run powers.

S9: every control tunes inside the allowed read/write/run/reach boundary. Inspection stays on. Lowering the read window changes how much is served at once; no setting permits secret paths or unlimited work. Provider changes are manual with a new preview, never automatic fallback.

D6, task memory and redaction

Raw questions, answers, tool results and drawer titles are session-only. D6 keeps raw chat out of files, logs and backups. The drawer holds up to 20 conversations per project; follow-ups carry up to 8 turns. App death clears the session.

A separate, narrowly bounded task-memory cache may persist admitted non-secret file snapshots and structured findings/decisions/plan under no_backup/ai/task/: at most five files, 160 KiB of file content and 256 KiB total. It is not a transcript. Last-task undo preimages are another bounded store under no_backup/ai/undo/. Project deletion or deleting a provider key clears those task/undo stores.

Run output and Explain last error use the same secret scan before character budgeting. Inspect previews and support exports anyway. These local rules do not guarantee that a provider retains nothing; retention is governed by separate provider terms. The local/on-device model remains postponed, not secretly available.

Finish the reading path—keep the review habit

You have reached Chapter 19 of 19. You can now distinguish source from output, local work from a push, a task preview from an approval, and a refusal from a broken feature. Keep tasks small, backups accessible and results observable.

Completing this reading path does not certify the review website. The owner’s Chapter 8 and P1/P5 device transcripts are still required. No public deployment is implied. See the review status.

Try it yourself

  1. Reject a proposed greeting edit and verify the original file remains; optionally Apply then Undo a fresh proposal without conflicting manual edits.
  2. Choose Skip on a run request and confirm no run. Optionally approve known safe code and compare actual output with the earlier expected lines.
  3. Lower the read window and check that inspection remains Always on. Explain a refused .env request using the name only—no real key or secret file.

Common mistakes

  • An edit proposal is not a write, and request_run is not execution.
  • Last-task Undo is not version control or a way to undo network effects.
  • D6 does not mean the provider has zero retention; task memory is not raw chat.
  • Do not try to widen caps or approvals with a different model, setting or prompt.
