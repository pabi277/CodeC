Files & Projects

Keep source in projects, understand what RUN creates and make a backup you can actually restore.

What you will learn

  • Create, import and open the right project context.
  • Separate source from temporary output and export safely.

Before you begin

A disposable project from earlier chapters; a file manager location outside CodeC private storage for backups.

Three ways into Projects

The Projects + sheet has New Project, Clone Git Repo and Import ZIP. Open Folder was removed in Phase46. To import a folder, zip the intended source files and import that ZIP; do not follow old linked-folder/mirror instructions.

  1. Create a project with Auto (detect) for an empty workspace, or a template such as C Program / Static Web for starter files.
  2. For a ZIP import, inspect the source first and choose a clear project name. Avoid dragging node_modules, build caches and unrelated private files into a practice import.
  3. For a clone, install Git and use a repository you can access. Chapter 11 explains credentials and remote truth.

One file is not the whole workspace

Tapping a project file opens that single file with its real path and autosave. Use a project card’s ⋮ → Open in editor to open the whole workspace with project chrome. In the Editor, the folder/breadcrumb opens Files & Projects and its Change picker can switch project or Single files.

Create files/folders in the drawer, rename deliberately and check imports/includes after a rename. Filename case matters. The file open when you tap RUN decides the active-source path for ordinary source files.

Source is valuable; binaries are rebuildable

CodeC-invented run outputs go under temporary run storage, CodeC/temp/runs. A path you explicitly name—such as cc hello.c -o bin/hello—stays where you asked for it. Do not assume an output is a backup of the source.

A named output folder

mkdir -p bin
cc hello.c -o bin/hello
./bin/hello

Expected: the same greeting as before. The bin directory can be regenerated. Keep your source, not just the executable.

Do not fight your ignore rules

CodeC uses .git/info/exclude for build artifacts and IDE metadata; it does not rewrite your .gitignore. Existing user rules, including intentional negations, win. Removing an artifact from tracking leaves the file on disk. Inspect Source Control before committing: generated output and secret files do not belong in the default source history.

Export before you need recovery

  1. Open Projects hub → ⋮ → Export all projects (backup ZIP). For one project, use its Export ZIP action.
  2. Save outside app-private storage, and verify you can locate the saved file. A ZIP stored only inside an app you are about to uninstall is not a safe backup.
  3. For an all-project backup, use Import projects backup on a clean/disposable target to check restoration. Avoid overwriting important work during a test.

Backup scope is source projects, not downloaded userland, settings, GitHub token or AI keys. Fresh installs require setup/sign-in again. Record expected files before testing restore; do not declare byte equality without checking.

Try it yourself

  1. Make a project with one C file and one text note; use whole-project and single-file opening and observe the difference.
  2. Export a disposable project and inspect that the source files are present. Expected: not merely a compiled binary.
  3. Rebuild a named bin/hello output, then inspect Source Control. Expected: source changes can be reviewed separately from generated artifacts.

Common mistakes

  • Do not teach or search for the deleted Open Folder action.
  • A same-phone private copy does not survive uninstall.
  • Large imports can stall a tree scan; reduce the archive to the relevant source.
