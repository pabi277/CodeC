Before you begin

Any earlier chapter; a copy of important source outside app-private storage before destructive recovery.

There is no universal “30 seconds means broken” rule for every operation. Huge tree scans and network stalls differ from scanf waiting for Enter. Avoid changing several variables at once.

When the program is the problem

A compiler line/column diagnostic means read that source location first. A crash inside your program may be an invalid pointer or bounds error; the app itself need not have crashed. Output that runs but is wrong is often logic: compare integer division, loop endpoints and the input you actually supplied.

Reduce to the tiny probe program from Chapter 4. If it runs, reintroduce changes one at a time rather than reinstall the app to fix a missing semicolon.

A repair ladder that preserves work

  1. Record the exact error and app version. Save/export source before any uninstall, Clear ALL Data or signing-channel switch.
  2. Check for an app update in Settings → About; use the signed release and checksum. A missing checksum opens Releases, not a blind installer.
  3. For package/setup faults inspect pkg status and follow the app’s heal/repair guidance. For compiler policy/ABI failures follow Output’s automatic fallback guidance—there is no engine selector.
  4. For repeated splash crashes, the third-launch Try starting without my settings path can bypass incompatible settings. Do not promise recovery of deleted private data.
  5. If still reproducible, report the evidence rather than retrying the same destructive action.

Read before sharing

Settings → Developer Options → View App Logs shows application evidence; Export App Logs opens a sharing action. Include the Device line with model/Android/ABI and relevant storage/mount information if present. noexec means a location cannot execute a binary; it is not a C syntax error.

A crash-log record is local until you share it. Inspect for source text, paths, credentials and personal content. Automatic secret redaction helps, but a screenshot of your own terminal can still expose a token.

Post a minimal, non-sensitive reproduction in GitHub Issues. Do not upload your whole private project to prove a small failure. Use in-app Feedback & Support for its provided contact options; this site does not publish personal developer contacts.

Known limitations are still part of the product

The FAQ keeps all eight beta issues visible: large trees, older 32-bit startup, sleeping jobs, credential restore, partial APKs, very long lines, crash loops and absent32-bit TCC. The correct remedy depends on the issue; one reinstall is not an answer to every row.

This is Chapter 17 of 19—not the end of the course. Next, learn how to ask about code and then how AI tools and approvals are bounded. No AI key is required just to read those lessons.

Try it yourself

  1. Create a harmless missing-semicolon error and record its location, then fix it. Expected: a clean compile, not an environment reinstall.
  2. Find your Device/log information and make a private redacted draft report. Do not post secrets as a test.
  3. Use the report template to explain one observed limitation, distinguishing what you measured from what you guessed.

Common mistakes

  • Do not reinstall five times before reading the first error.
  • A local commit, an AI explanation and a package badge are not proof of successful remote execution.
  • Never disable signature checks or mix repositories to silence an error.
